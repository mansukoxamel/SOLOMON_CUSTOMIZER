Level Data Model Matrix - 敵/アイテム/ブロックID整理

この資料は、SOLOMON_CUSTOMIZER が扱うステージ内要素を 「敵」「アイテム」「ブロック」「メタ情報」に分け、 原作ROMと mapper66 拡張ROMで何バイト単位のデータとして管理しているかを整理する。 結論だけ言うと、敵とアイテムはおおむね ID 1バイト + 位置 1バイト、 原作ブロックは 1マス1バイトではなく2枚のbitmask、 拡張ROM/runtimeでは扱いやすい1セル1バイト形式へ寄せている。

2. ID範囲の見方: 原作実使用 / 形式上限 / 改造余地

ここが重要: 「原作で実際に使っているID」と「データ形式として表せるID数」は別。 さらに「ゲーム側のAI/描画/取得処理まで意味を持つID」はまた別。 下表は、JP原作ROM ROM/Solomon no Kagi (J).nes の実データを load_all_levels() と同じ読み方で集計した値を含む。

敵ID

原作実使用 38種類

保存形式だけなら 最大255種類。$00 は終端なので通常IDは $01-$FF。

アイテムID

原作ベース 34種類

現行形式のベースIDは下位6bitなので 最大64種類。状態bit込みの原作実使用値は81種類。

原作ブロック

形式上 4状態

茶bit/白bitの2枚で表す。1セル1バイト化すれば最大256状態へ拡張可能。

敵ID 原作実使用と上限

原作JP実使用
38種類。範囲は $1C-$81 だが連続ではない。
実使用ID
$1C, $1D, $24, $25, $26, $27, $28, $29, $2A, $2B, $2C, $2D, $2E, $2F, $30, $32, $34, $36, $3C, $3E, $40, $42, $44, $46, $48, $4D, $68, $69, $6D, $70, $71, $74, $75, $78, $79, $7D, $80, $81
形式上限
敵IDフィールド自体は1バイト。ただし $00 は敵リスト終端なので、通常の敵IDとして素直に使えるのは 最大255種類、$01-$FF。
さらに増やすなら
敵リストを「終端$00」ではなく「個数+配列」に変えるなら $00 も敵IDにできる。IDを2バイト化すれば256種類を超えられるが、敵AI dispatch、グラフィック、当たり判定、生成処理、ミラー敵セットもまとめて拡張が必要。
ここでいう255種類は「保存形式が受けられる」上限であり、全IDが正しく動くという意味ではない。

アイテムID 原作実使用と上限

原作JP実使用
状態bit込みの実使用値は81種類、範囲は $04-$B3。ベースアイテムとして見ると34種類。星座は別枠で12種類、$F0-$FB。
ベース実使用ID
$04, $08, $0C, $0E, $11, $12, $13, $14, $15, $16, $17, $18, $19, $1B, $1C, $1D, $1E, $1F, $22, $25, $26, $27, $28, $29, $2A, $2B, $2C, $2D, $2E, $2F, $30, $31, $32, $33
現行形式上限
通常アイテムは下位6bitがベースIDなので 最大64種類、$00-$3F。ただし $00 単独はストリーム終端なので、通常可視アイテムとしては扱いに注意が必要。
値域の消費
$40 と $80 は隠し/ブロック内の状態bit。$C0-$DF は圧縮命令、$E0-$EF は終端、$F0-$FB は星座。
さらに増やすなら
状態bit、圧縮命令、終端、星座を別フィールドへ逃がす形式に変えれば、アイテムID 1バイトを丸ごと $00-$FF の 256種類 に使える。それ以上はID 2バイト化。
増やす場合は、アイテム取得処理、描画、スコア/効果dispatch、PNG/XML保存形式、圧縮形式を同時に変える必要がある。

原作ブロック 原作実使用と上限

原作JP実使用
読み込み後の分類では NONE, BROWN, WHITE の3種。茶bit+白bitの両方ONも形式上はあり、アプリでは白へ正規化する。
形式上限
原作の地形形式は茶bit/白bitの2枚なので、1マスあたり2bit相当。形式上は 4状態。
さらに増やすなら
mapper66拡張ROMのように1セル1バイト化すれば、セル値としては最大256状態を持てる。ただしゲーム中で意味を持たせるには、描画、衝突、破壊、復元、死亡後再描画のruntimeが必要。

3. 位置1バイトの共通ルール

敵・アイテム・鍵・扉・開始位置・ミラー位置など、多くの「座標」は1バイトで表す。 下位4bitがX、上位4bitがY+1。Yに+1が入るため、画面外や削除扱いを表す時は アプリ内部で (0, -1) のような形も使う。 
位置byte = ((y + 1) & 0x0F) << 4 | (x & 0x0F)
x = byte & 0x0F
y = (byte >> 4) - 1

値域意味注意

5.1 状態bitの見方

base item id = element_no & $3F
$40 = hidden
$80 = in block
$C0 = white in-block / またはストリーム制御域
注意: $C0 以上は「白ブロック内アイテム」として扱う場面と、 原作アイテムストリームの「圧縮/終端/星座」として扱う場面がある。 単独の1バイトだけを見て決めず、読み出している場所と文脈を見る。

6. 原作ブロックデータ

原作ステージの地形は、16x12=192マスを1マスずつ1バイトで持っていない。 茶ブロック用のbitmaskと白ブロック用のbitmaskを別々に持つ。 それぞれ192bit=24Bなので、1面の地形は48B固定。

茶bit白bitCustomizer内部意味
00Wall.NONE空気
10Wall.BROWN茶ブロック
01Wall.WHITE白ブロック
11Wall.BROWN_WHITE茶+白の複合状態。壊せる白系として扱う
1面の原作地形:
  茶ブロックbitmask 24B
  白ブロックbitmask 24B
  合計 48B

7. mapper66拡張ROMとruntimeセル

このカスタマイザーの通常編集対象は、アプリが生成する日本版 mapper66 wide-title 拡張ROM。 拡張ROMでは、原作の圧縮/bitmaskだけでは表現しづらい特殊セルを扱うため、 固定セル・mask・部屋別補助表を追加している。

例主な値/形式目的
白ブロック内アイテム$C0 + item_id 系見た目は白ブロック、中身はアイテム
壊せる白ブロック$F9 runtime特殊セル描画と実体変換を分ける
すり抜ける白ブロック$FA runtime特殊セル見た目だけ白、実体は空気
ひび割れブロック$01 + 補助リスト/mask死亡後復帰や中身再注入を制御
透明ブロック内アイテム24B bitmask + 通常アイテム通常アイテム表示をruntimeでブロック内へ変換

8. まとめ

質問答え
敵の種類は1バイト?はい。敵ID 1B + 位置1B。
アイテムの種類は1バイト?ほぼはい。ただし上位bitに隠し/ブロック内状態が混ざり、C0以上は制御値にもなる。
ブロックの種類は1バイト?原作ROMでは違う。茶/白2枚のbitmaskで48B/面。
拡張ROMでは?1セル1バイトに近い扱いもある。特殊セルやruntime変換のため、maskや補助表も併用する。
