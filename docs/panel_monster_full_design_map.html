7. 現在の問題点

方針1: cacheは残す。PRG0を削る。
全ステージ共通の6B値はPRG1へ置き、loaderでRAMへコピーし、PRG0 helperがRAMから読む。 PRG1とRAMは荷物置き場、PRG0は狭い通路として扱う。 直接operand化でPRG0が太る変更は、まともに動くROMができるまで入れない。
方針2: cache helperはPRG0節約の部品として扱う
$BE62 interval helper、$BE9F group RAM offset helper、$BEBD speed selectorがcache前提。 ここは撤去候補ではなく、短く保つ対象として見る。
問題3: 親drift対策と共通物理の責務が曖昧
current 6df3733は $866D speed initializer hookで速度を消す。 ただし、どの段階で $8689 common physicsが走るかは別問題で、probeではここを明確に分けて見る必要がある。
問題4: Bullet markerの観測点を間違えると結論が崩れる
markerはchild sub-slot +7。main-slot +7 はY座標。 Mesen probeではこの区別を最初に固定する。

8. v2 Foundation設計

読み方: この章は「cacheを消す小修理」ではない。 cacheはPRG0を削るために残す。Panel Monster v2で分類・fire・Bullet・parent契約を統一し、 旧prototypeと旧standalone計画を消して、最新runtimeだけで判断する土台を作る。

8.1 作業順

順番作業理由成功条件
1 この設計図を基準にする。 接続全体を固定しないままコードを削ると、loader/cache/Bullet/AIが混ざる。 どのhelperが何を読むか説明できる。
2 global cache経路をv2契約として固定。 直接operand化よりPRG0が短い。 $0740-$0745 をA/B/C helperだけが読む。
3 interval/speed helperをcache契約の短いreaderとして維持。 ユーザー値をPRG1に置き、PRG0の分岐と即値を増やさない。 $BE62/$BEBD/$E92C の責務が説明できる。
4 runtime loaderの6B copyを検証対象として固定。 StageExt/Seal/visible item side effectsとA/B/C cache copyを混同しない。 global cache tableとloaderが保存ROMへ書かれる。
5 ROM/RAM管理簿と RESERVED_SPANS を同時更新。 空き領域誤認を防ぐ。 room_flags._verify() が通る。
6 Mesen probeで動作確認。 静的署名だけではBullet/親driftは確定しない。 global cache copy正、Bullet marker正、A/B/C方向正。

12. 全体組み直し用の仮置き場

判断: Panel Monster周辺を全部組み立て直す場合、いきなり現在のhook/caveへ分割配置してはいけない。 まず仮置き場で一体runtimeとして組み、入口・出口・サイズ・破壊レジスタ・RAM副作用を確認してから、本番配置へ分解する。

12.1 仮置き場は2種類に分ける

種類場所目的本番ROMに残すか
Build-time staging blob Python生成上の仮想base address Panel Monster全体runtimeを一つの連続blobとして設計し、内部entry/label/branch/sizeを検証する。 残さない。設計とサイズ計測用。

12.2 なぜ仮置き場が必要か

理由説明仮置きなしで起きる問題

12.4.1 共通化の採否ルール

禁止: 「統合すれば必ず小さくなる」という前提で進める。

共通化のために入口判定が増えすぎる場合、きれいに見えてもROMサイズは増える。サイズが増える共通化は採用しない。

対象方針理由
通常Panel入口専用入口のまま残してよい。共通入口で毎回Panel種別判定を増やすより短い可能性が高い。
2-way / 3-way入口専用入口のまま残してよい。発射数とmarker列が決まっているため、入口で決め打ちした方が短い場合がある。
A/B/C入口専用入口のまま残してよい。A/B/C group判定、interval決定、親drift消しを毎回共通分類器へ戻さない。
child Bullet生成後のmarker書込共通化候補。処理が同じで、分岐を増やさず共有できる。
Bullet marker decode共通化する。$88-$8B を同じ表とdecoderへ通す必要がある。
2x/3x substep collision loop共通化する。同じloopでextra countだけ変えるのが正しい契約。
Panel見た目分類共通化候補。ただし呼び出し回数を制限する。property/animationには有効だが、hot pathで何度も呼ぶと太る。
採用基準: 共通化は「同じ処理をまとめる」ためにだけ行う。 分岐や判定が増えてサイズが大きくなる場所は、専用ルートとして分けたままにする。 判定はできるだけ入口で1回だけ行い、その後は決め打ちのrouteで進む。

12.5 仮置き場の候補と禁止

禁止: 空いていそうなPRG0へ直接置く。

禁止: 既存hook先を一部だけstaging版へ差し替え、残りを旧runtimeに繋いだ混在状態を長く残す。

禁止: Mesen確認用のROM-side stagingを本番仕様として扱う。

推奨: まずbuild-time staging blobで全体設計とサイズを固める。 実機確認が必要になった段階で、PRG1 reserveまたは明示した実験用PRG0候補へ一時配置し、検証後に本番配置へ分解する。

12.6 既存機能を一時停止して貸すprobe profile

ROM上に空きがない場合は、別機能の予約領域を一時停止し、Panel MonsterのROM-side stagingへ貸すことはできる。 ただしこれは検証ROM専用であり、保存ROM、本番配置、通常リリースには含めない。 目的は「Panel Monster全体を一度まとまった形で動かし、fire path、bullet path、親/子状態、A/B/C差分をMesenで観察する」ことに限定する。

候補借り方使ってよい条件注意
stage announcement cluster stage_announcement.py が使うPRG0断片をprobe ROMで無効化して貸す。 ステージ開始演出や警告表示を検証対象にしない。 比較的借りやすいが断片配置なので、一体blob全体をそのまま置く場所にはならない。
visible / white / cracked in-block helpers 該当ブロック機能を使わないprobe roomに限定して一時停止する。 Panel Monster検証ステージ内で該当ブロックや隠しアイテムを使わない。 ステージ挙動が変わるため、通常プレイ確認には使わない。
key enemy runtime key enemyを含まないprobe room専用で候補にする。 鍵、扉、fairy/door light系の検証を同時に行わない。 周辺連動が大きいので、借りる前にentry/hook一覧を別表で固定する。
later-bank emergency reserve 0x67D1-0x681B 付近の小さいreserveをtrampolineや小helperに使う。 75 bytes級の小処理で足りる。 705 bytes級の組み直し本体は入らない。
PRG1 reserve bank状態が保証できる地点だけ、probe staging本体の置き場として使う。 呼び出し時点のmapper bankが固定でき、PRG0 fixed bankから安全に到達できる。 PRG0から常時JSRできる場所ではない。入口ごとにbank1実行中か、RAM trampoline/bank switch bridgeが必要かを先に表へ出す。

貸してはいけない: Panel Monsterとの共存確認対象であるSpark Ball、Gargoyle、Saramandor周辺を先に潰す。

貸してはいけない: 原作の敵speed/state tableや $DB99-$DBDE など、意味が確定していない本体データ領域をprobe用途で上書きする。

貸してはいけない: probeで動いた一時停止構成を、そのままproductionの省スペース策として採用する。

実装方針: panel_probe_runtime_profile のような明示名で、通常保存経路とは別の検証ROM生成スイッチにする。 スイッチを入れた時だけ借用対象featureを無効化し、Panel Monster staging entryへhookを向ける。 検証が終わったら、測定したサイズとentry契約だけを本番再配置へ持ち帰る。
PRG1 staging前チェック: PRG1へ本体を置く場合は、各entryについて「その時点でbank1が見えているか」を必ず確認する。 PRG0 fixed bankから入るhookは、PRG1へ直接 JSR しない。 bank保証がない入口では、RAM trampolineか明示的なbank switch bridgeを設計してから使う。
