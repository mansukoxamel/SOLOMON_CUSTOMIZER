新敵ID分類フロー

対象: 日本版 mapper66 wide-title 拡張ROMで、新しい敵IDを原作IDの間借りではなく独立IDとして扱う設計。

結論: 新敵IDは、1回だけ判定すれば終わりではない。ゲーム中では少なくとも 敵生成時、初期セットアップ時、毎フレームAI時 の3段階で、 同じ敵IDに対して別の質問をしている。

1. ステージデータを読む段階

ここは今回の分類設計の本命ではない。ステージデータから必要になるのは、基本的に敵IDと座標だけ。

ステージ敵データ
  ↓
敵ID $84 と 座標を読む
  ↓
敵配置リストとして保持する

この段階では、まだ「どのAIか」「どのアニメか」「倒せるか」は決めなくてよい。

2. 敵を生成する時

ステージの敵リストから、実際に画面内の敵スロットへ入れる時。ここで最初の分類が必要になる。

敵ID $84 と座標を読む
↓
空いている敵スロットを探す
↓
そのスロットに type=$84, X, Y, status などを書く

ここで聞いている質問

この敵IDは何者か？
$84 は普通の原作敵か？
$84 は追加敵か？
追加敵なら property/status は何か？

property は、ざっくり言うと敵の初期性格。

  • この敵は当たれるか
  • 火球で倒せるか
  • 重力を受けるか
  • 最初にジャンプ状態になるか

今回の $84 では、接触判定あり、火球で倒せる、status は $E0 系にしたい。

3. 敵の初期セットアップ時

敵スロットに入った敵を、ゲームが動かせる形に整える時。ここで2回目の分類が必要になる。

生成直後:
  type=$84
  X=13
  Y=7
  status=...

まだ足りないもの:
  どの速度テーブルを使う？
  どのアニメ表を使う？
  最初の絵はどこ？
  アニメの進み方は？

ここで聞いている質問

$84 はどの敵グループとして初期セットアップする？

今回ここを外した時、$84 はゴースト/ヌエル系に寄った。理由は、$84 のまま原作式で分類すると Flame ではない別グループの表を見に行ったため。

$84 の必要な答え: Flame 系の setup group $40 として扱う。

この分類は「見た目」と「速度」に効く。特に $8AC0-$8B50 の流れでは、$D9D3 系の速度/セットアップ表だけでなく、$D0E8 系のアニメ初期ポインタにもつながる。

4. 毎フレームのAI実行時

ゲームが動いている間、敵ごとに毎フレーム呼ばれる。ここで3回目の分類が必要になる。

今いる敵スロットを見る
↓
type を見る
↓
その敵のAIへ飛ぶ
↓
動く、止まる、弾を撃つ、反射する、など

ここで聞いている質問

$84 はどのAIを実行する？

今回の $84 は「倒せるが動かないWhite Flame系」なので、AI入口ではFlame AI $A5A0 へ送る。ただし表示アニメは別フックで止め、固定2タイル表示にしている。

5. 判定は3回ある

段階聞いていること$84 の答え
敵生成時IDから property/status 系を決めるstatus $E0、接触あり、火球で倒せる
初期セットアップ時IDから speed/animation/setup group を決めるFlame setup group $40
毎フレームAI時IDからAI処理を決めるFlame AI $A5A0 へ送り、初期behaviorはWhite Flame寄りの $14

つまり、同じ $84 を見ているが、各段階で聞いている質問が違う。

火球ヒット時の注意: Ice Flame のAI hookは、$84 だけを追加敵としてFlame AIへ送る。 追加敵ではないIDは、hook入口で渡された原作AI番号を復元してから $A329 へ戻す必要がある。 ここを壊すと、火球ヒット後に敵が $14 の撃破/拾得エンティティへ変わった時、通常AI dispatch が崩れる。

6. なぜ共通分類窓口が必要か

何も考えずに作ると、3か所それぞれで直接こう書くことになる。

生成時:
  $84 か？ → property を変える

初期セットアップ時:
  $84 か？ → Flame setup にする

毎フレームAI時:
  $84 か？ → Flame AIへ送る

これは $84 だけなら短い。しかし、将来 $85, $86, ... と増えると、各入口に敵ID判定が散らばって管理不能になる。

悪い増え方: 各フックの中に $84なら...、$85なら...、$86なら... を個別に積む。

7. PRG0だけでやる場合の整理された形

PRG0だけでやるなら、まず「敵IDから追加敵indexを返す小さい共通関数」を1つ作る。

input:
  enemy ID = $84

output:
  追加敵 index = 0

将来はこう増やす。

$84 → index 0
$85 → index 1
$86 → index 2
...

各段階では、直接 $84か？ を何度も書かず、共通分類関数で index を取ってから、それぞれ必要な表を見る。

敵生成時:
  index = classify(enemy_id)
  status = status_table[index]

初期セットアップ時:
  index = classify(enemy_id)
  setup_group = setup_table[index]

毎フレームAI時:
  index = classify(enemy_id)
  ai_mode = ai_table[index]

8. 小学生向けの言い方

敵ID

敵の名札。

$84 は「新しい炎」の名札。

生成時

名札を見て「体の性質」を決める。

倒せるか、当たれるか、重力を受けるか。

初期セットアップ時

名札を見て「使う絵と速さ」を決める。

炎の絵か、ゴーストの絵か、どの速度か。

毎フレームAI時

名札を見て「今日どう動くか」を決める。

止まる、歩く、弾を撃つ、反射する。

10. 設計上の注意

  • 共通分類関数で分かるのは「追加敵か」「追加敵なら何番か」まで。
  • 生成時、初期セットアップ時、毎フレームAI時で欲しい答えは違う。
  • そのため、status_table、setup_table、ai_table のように用途別の表を持つ。
  • PRG0だけでやる場合、分類表もPRG0内に置く。RAMやPRG1へ逃がさない前提なら、表のバイト数を常に意識する。
  • 最初の1体だけを見ると共通分類窓口は大きい。将来20体、30体へ増やす前提で、判定の散らばりを防ぐための設計。
